garner 0.2.2 gives the registry a hostname of its own and fixes bugs from a code review where one package, uploaded or synced, could break apt for every client of its suite or stop publishing altogether. It also changes how apt hosts get the signing key and how conflicts are reported.

## A hostname for the registry

`oci.public_url` gives images a hostname of their own, such as `https://registry.example.com`. garner answers `/v2/` on every host it receives, so references to `server.public_url`'s host keep working; the reverse proxy decides which hostnames serve it. The registry URL is now always a scheme and host: with a path in `server.public_url`, the UI's tag-list links pointed below that path, where no registry answers. ([06b9d7f](https://github.com/avesst/garner/commit/06b9d7f))

## Changes that may need action

- The apt client file (`<client_name>.sources`) now carries the signing keys inline in `Signed-By`, and the UI's instructions install only that file. Hosts set up with the old instructions keep working, since `/key.gpg` is still published. To move one over, download its `.sources` file again and delete `/usr/share/keyrings/<client_name>.gpg`. When you rotate keys, apt hosts now need the new `.sources` file rather than the keyring. Inline keys need apt 2.4 or later, which every supported release has. ([d37e138](https://github.com/avesst/garner/commit/d37e138))
- Packages that would break clients or publishing are now refused with `400`, and the message names the problem. This applies to uploads and synced assets alike. No package in Debian 13, Ubuntu 24.04 or a sample of Fedora 44 and Enterprise Linux 9 and 10 is refused.
  - deb relationship fields (`Depends`, `Breaks`, `Provides` and the others apt reads) that dpkg cannot parse ([721bc70](https://github.com/avesst/garner/commit/721bc70))
  - control characters, such as ANSI colour codes, anywhere in an rpm's header text ([5d25ecb](https://github.com/avesst/garner/commit/5d25ecb))
  - a package whose pool file name would be longer than 200 bytes ([5692d38](https://github.com/avesst/garner/commit/5692d38))
  - a deb control file larger than 512 KiB, down from 1 MiB ([efe8980](https://github.com/avesst/garner/commit/efe8980))
- Only ownership conflicts, deliveries held for `garner approve`, are open now, and approving or removing the package closes them. Sync conflicts, such as a checksum mismatch, are recorded as history: `garner conflicts list --all` shows them. `garner_conflicts_open` therefore returns to 0 once held packages are decided. To be alerted of sync conflicts, use the new counter `garner_conflicts_total{kind}`, for example `increase(garner_conflicts_total[1h]) > 0`. ([ff95715](https://github.com/avesst/garner/commit/ff95715))

## Fixes

- One package with a malformed relationship field, such as `Depends: libc6 (>= 2.31` without its closing parenthesis, made `apt-get update` fail on every client of its suite, for the distribution's own repositories too, until the package was removed. `garner verify` did not notice. ([721bc70](https://github.com/avesst/garner/commit/721bc70))
- One rpm with a control character in its summary, description or changelog made every publish fail, in every format, with createrepo_c 1.1.2 (garner's container image) and 1.2.0 (Debian 13). Uploads went on returning 200 but were never published. ([5d25ecb](https://github.com/avesst/garner/commit/5d25ecb))
- A package whose pool file name was longer than 255 bytes was accepted, and from then on every publish failed with "file name too long". ([5692d38](https://github.com/avesst/garner/commit/5692d38))
- A deb control file just under the old 1 MiB limit became a `Packages` stanza that apt cannot parse, which broke apt for every client of the suite. ([efe8980](https://github.com/avesst/garner/commit/efe8980))
- In the container image, and on hosts with rpm 6, garner could not re-sign an rpm its vendor had already signed: uploads failed with 500, syncs retried it on every poll, and a key rotation stopped there. garner installed from the `.deb` on Debian was not affected. ([af40d88](https://github.com/avesst/garner/commit/af40d88))
- Under a restrictive umask such as 027 or 077, the UI's apt instructions created a keyring apt could not read, and `apt update` failed with "OpenPGP signature verification failed". ([d37e138](https://github.com/avesst/garner/commit/d37e138))
- Nothing resolved a conflict, so the open count in `garner status`, the UI and `garner_conflicts_open` only grew, and an alert on it never cleared. ([ff95715](https://github.com/avesst/garner/commit/ff95715))
- GC could delete the temporary directory of a sync that was still running, which then failed with "no such file or directory". ([2ca1cb4](https://github.com/avesst/garner/commit/2ca1cb4))

Full list of changes: https://github.com/avesst/garner/compare/v0.2.1...v0.2.2

garner is in early development and is not ready for internet-facing use. Configuration and behaviour may change between 0.x releases.
