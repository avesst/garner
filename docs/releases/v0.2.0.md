garner 0.2.0 adds container images: garner is now a repository for packages and container images. It also lets synced releases wait before they are published, checks the published repository the way clients read it, and fixes several bugs, two of them in how uploaded packages are read.

## Container images

With an `oci` section, garner is a container registry at `/v2/` on its host. CI pushes with `docker push`, using a token with the `upload` scope as the login, and hosts pull with `docker pull` without logging in. Image names are owned like package names. Multi-platform images and indexes are stored whole, and tags move when you push them again; the digest a tag pointed at stays pullable until `oci.retention` ages it out, so deployments that pin digests keep working.

Images can also be synced from other registries, such as ghcr.io, Docker Hub and GitLab's registry: add the registry under `registries` and a source with `registry`, `image` and the `tags` to copy. A synced tag moves only when it moves upstream, so a rollback or a deleted tag holds until then.

Images are published in snapshots like packages, so `garner snapshot rollback` restores their tags too. Behind a reverse proxy, pass all of `/v2/` to garner; the README has Caddy and nginx examples. Docker, podman, skopeo and crane are tested as clients.

## Waiting before publishing synced releases

`min_release_age`, in `defaults` or per source, holds a synced release back until it is that old, so a compromised release has time to be noticed and pulled before garner publishes it. It applies to synced images as well. Waiting releases are listed in `garner status`, and `garner sync SOURCE --ignore-age TAG` lets one through. It is off by default; uploads are not affected.

## Checking the published repository

`garner verify` checks that what garner serves matches its database, reading it as apt, dnf and container clients do: signatures against the published key, every index file by size and checksum, and every package and image down to its files. It runs through the API, so it works while the server runs, and `--config-hash` waits until a configuration you just pushed is published, for use in CI. It exits 1 on errors, and with `--strict` on warnings.

## Landing page

The landing page has a tab per kind of repository (Linux packages, container images) with how to use it, counts, the health of its sources and every package or image, filterable.

## Changes that may need action

- With `i686` in `rpm.architectures`, i686 packages are now listed in the x86_64 repository, as Fedora and Enterprise Linux ship multilib, and the separate `rpm/<release>/i686` repository is gone. `i686` now requires `x86_64` in the same list.
- `POST /api/v1/sync` rejects a body that is not empty or the documented JSON.
- A GitLab release deleted and re-created under the same tag is now synced again as a new release.

## Fixes

- A rollback to a snapshot published while a format was disabled marked all of that format's packages as removed, and GC later deleted them. Rollbacks now leave formats the snapshot did not include alone.
- An rpm with repeated identity tags could pass the ownership check under one name and be published under another. Such headers are now rejected. Identical repeated tags, which AlmaLinux 10 rpms built since mid-2025 have, are accepted; garner refused most of them before.
- A small crafted `.deb` could take minutes of CPU to read. Reading it now takes time in proportion to its size.
- A signing key exported with `gpg --export-secret-subkeys` and a passphrase failed at every publish. It now works, and a key garner cannot use fails at start.
- A reload sent while garner was starting under systemd stopped it, and the reload was lost.
- GC deletes packages much faster on large repositories: 200 packages among 100,000 took 55 seconds, long enough to make uploads time out, and now take a fraction of a second.

garner is in early development and is not ready for internet-facing use. Configuration and behaviour may change between 0.x releases.
